# Arquitetura — Portal Alvim Análises

Este documento registra as decisões de arquitetura desta primeira etapa do projeto e como estendê-lo sem precisar de grandes refatorações.

## 1. Visão geral

Monorepo gerenciado por Turborepo + npm workspaces:

- `apps/backend` — API REST em NestJS + Prisma + PostgreSQL, com autenticação JWT própria.
- `apps/web` — Next.js (App Router), painel administrativo e portal do cliente num único app, com rotas separadas por grupo.
- `apps/mobile` — Expo (React Native + Expo Router), app para técnicos (agenda) e clientes (consulta).
- `packages/shared` — tipos, enums e constantes TypeScript usados pelas 3 apps (única fonte de verdade para contratos de API e regras de navegação por papel).

## 2. Clean Architecture no backend

Cada módulo de negócio "completo" (`users`, `clients`, `contracts`, `schedules`) segue três camadas:

```
modules/<nome>/
  domain/           entidade + interface do repositório (porta)
  application/      DTOs + use-cases (dependem só da interface do repositório)
  infrastructure/   controller HTTP + implementação Prisma do repositório
```

Use-cases dependem da **interface** do repositório via token de injeção de dependência (`CLIENT_REPOSITORY`, `USER_REPOSITORY` etc.), nunca do `PrismaService` diretamente. Isso é o que permite trocar a infraestrutura (ex.: outro banco, cache, mock em teste) sem tocar a regra de negócio. `clients/` é o módulo de referência desse padrão — replique sua estrutura ao criar um módulo novo.

Exceções propositais, documentadas para não gerar confusão:

- **`auth/`**: mesma ideia, mas mais enxuto — "autenticação" não é uma entidade de negócio com invariantes próprias, então não há uma pasta `domain/` com entidade.
- **`service-types/`**: lookup simples (CRUD trivial, sem regra de negócio), implementado como `service.ts` + `controller.ts` direto, sem a separação em camadas.

## 3. Módulos completos vs. stub

| Módulo | Estado | Observação |
|---|---|---|
| `auth` | Completo | Login, refresh, logout, me |
| `users` | Completo | CRUD, apenas ADMIN cria/edita |
| `clients` | Completo | CRUD + `/clients/me` |
| `contracts` | Completo | CRUD + gestão de escopo (`ContractScope`) |
| `schedules` | Completo | CRUD + transição de status |
| `service-types` | Completo | Lookup simples |
| `sampling-point-standards` | Completo | Lookup simples (mesmo padrão de `service-types`) |
| `sampling-points` | Completo | CRUD por empresa (`?clientId=`), ADMIN/MANAGER |
| `compounds` | Completo | Lookup simples (mesmo padrão de `service-types`) — os 14 compostos analisados (Siloxanos, VOCs, Metais, etc.) |
| `samples` | Completo | CRUD ligado a `Schedule` + `SamplingPoint` (opcional) + `Compound` (obrigatório), `?clientId=`/`?scheduleId=`/`?compoundId=` |
| `attachments` | Infraestrutura pronta, sem rota pública | `FileStorageService` implementado (adapter local), consumido internamente pelos módulos abaixo quando forem construídos |
| `mail` | Completo | `MailService` (Resend) — usado hoje só por `schedules/send-to-client`; sem controller próprio |
| `service-executions` | **Stub** | Schema Prisma + migration prontos; repositório mínimo; sem controller |
| `certificates` | Completo | CRUD + upload/download/substituição de arquivo (multipart), `?sampleId=` |
| `notifications` | **Stub** | Idem — sem emissor real (e-mail/push) |
| `dashboard` | Parcial | Só `/dashboard/summary` com 4 agregados básicos |

"Stub" significa: o modelo de dados já existe e migra normalmente, mas **não há endpoint HTTP exposto** — implementar o controller/use-cases é trabalho de uma fase futura, seguindo o mesmo padrão de `clients/`.

## 4. Modelo de dados — decisões

- **Tipos de serviço extensíveis**: `ServiceType` é uma tabela (lookup), e `ContractScope` é a tabela de junção entre `Contract` e `ServiceType`. Adicionar um novo tipo de serviço é um `INSERT`, não uma migration.
- **Checklist da execução do serviço em JSON** (`ServiceExecution.checklistData`): mais simples para a fase 1, que não precisa consultar/reportar por item individual do checklist. Se isso mudar, migrar para uma tabela `ChecklistItem` (`serviceExecutionId`, `label`, `checked`, `order`) preservando `checklistData` como fallback durante a transição.
- **Attachment genérico com discriminador `kind`**: uma única tabela `Attachment` (`PHOTO` | `ATTACHMENT_FILE` | `CERTIFICATE_PDF`) em vez de tabelas por tipo de arquivo. `storageKey` é opaco ao domínio — só o `FileStorageService` sabe resolvê-lo.
- **`clientId` denormalizado em `Schedule` e `Sample`**: evita join through `Contract`/`ServiceExecution` só para aplicar o filtro de RBAC do papel Cliente. Trade-off aceito: ao mover um contrato entre clientes (cenário raro), os agendamentos já criados manteriam o `clientId` antigo — se isso virar um caso real, adicionar uma rotina de reconciliação.
- **Pontos de amostragem por empresa + tipo padrão opcional**: `SamplingPoint.name` é o nome que cada empresa usa pro próprio ponto (varia por cliente); `SamplingPoint.standardId` é uma marcação opcional para um `SamplingPointStandard` (lookup extensível, mesmo padrão do `ServiceType`) — permite comparar o mesmo tipo de ponto (ex.: "1ª Barreira (ANP)") entre empresas diferentes no futuro, mesmo que cada uma o chame de um jeito.
- **`Schedule.contractId` é opcional**: agendar um serviço não exige selecionar um contrato — só empresa, tipo de serviço, técnico e data. `contractId` continua existindo (nullable) para permitir vincular a um contrato depois, se fizer sentido (ex.: faturamento, relatórios por contrato). `Schedule.serviceTypeId` (obrigatório) é quem hoje representa "qual serviço" está sendo agendado, independente de contrato.
- **`Sample` liga em `Schedule` (+ `SamplingPoint` opcional), não em `ServiceExecution`**: o desenho original do stub ligava amostra a `ServiceExecution` (execução do serviço, ainda stub). Como o agendamento já carrega os pontos de amostragem da visita (`ScheduleSamplingPoint`), faz mais sentido a amostra apontar direto pro agendamento e, opcionalmente, pra qual ponto especificamente foi coletada — dispensa esperar o módulo `service-executions` sair do stub pra ter Amostras funcionando. `ServiceExecution` continua existindo (schema pronto) para quando o registro de execução em si (checklist, horários) for implementado.
- **`Schedule` ↔ `SamplingPoint` é N:N** (`ScheduleSamplingPoint`): uma visita pode cobrir vários pontos de amostragem da empresa (ex.: "1º Barreira" e "2º Barreira" no mesmo agendamento). No formulário, a lista de pontos disponíveis é filtrada pela empresa selecionada (`GET /sampling-points?clientId=`), e a seleção é limpa se o usuário trocar de empresa antes de salvar. `PrismaScheduleRepository.update()` substitui o conjunto inteiro de pontos (apaga e recria dentro de uma transação) quando `samplingPoints` é enviado — mesmo padrão usado em `PrismaUserRepository.update()` para os vínculos usuário-empresa.
- **`Compound` como lookup extensível + `ScheduleSamplingPointCompound`**: os compostos analisados (11000-Siloxanos até 26000-NOx) são registros em `Compound`, não um enum — mesmo racional do `ServiceType`. Cada `ScheduleSamplingPoint` (o vínculo agendamento↔ponto) tem seu próprio conjunto de compostos via `ScheduleSamplingPointCompound`, porque o mesmo agendamento pode amostrar compostos diferentes em cada ponto (ex.: "1º Barreira" com Siloxanos+H2S, "2º Barreira" só com H2S). O formulário (`ScheduleForm.tsx`) renderiza um `MultiSelect` aninhado por ponto selecionado, e `PrismaScheduleRepository` cria/recria essa estrutura de três níveis (`samplingPoints → compounds`) dentro da mesma transação de update.
- **`Schedule.endDate` opcional para serviços de múltiplos dias**: `scheduledDate` continua sendo obrigatório (data de início); `endDate` é nulo para serviço de um dia só. Removido o campo de horário (só datas) — o agendamento passou a ser por dia, não por horário específico, já que na prática o serviço pode se estender por vários dias consecutivos.
- **`Sample.compoundId` obrigatório**: toda amostra coletada é de um composto específico (um dos 14 cadastrados), refletindo a estrutura de pastas físicas que a Alvim já usa (11000, 12000, ...). `analysisType` (texto livre) virou opcional — era o campo antigo antes de existir o lookup de composto, mantido para observação livre quando necessário.
- **UI "Amostras" como pastas por composto**: a tela `/amostras` lista uma "pasta" (card) por `Compound` ativo, espelhando a estrutura de diretórios que a empresa já usa no Explorer (11000-Siloxanos, 12000-VOCs, etc.). Entrar numa pasta (`/amostras/composto/[compoundId]`) filtra as amostras daquele composto; criar uma amostra a partir de dentro de uma pasta pré-seleciona o composto via querystring. O upload da cadeia de custódia (PDF) é um trabalho futuro que entra nessa mesma tela, reaproveitando `Attachment`/`FileStorageService` já prontos.
- **`Schedule` ↔ `User` (técnico) é N:N** (`ScheduleTechnician`): um serviço pode precisar de mais de um técnico em campo (ex.: monitoramento com equipe). Substituiu o antigo `Schedule.technicianId` único — a migration `schedule_multi_technician_and_order_number` cria `schedule_technicians`, faz backfill copiando os vínculos existentes e só então remove a coluna antiga. `applyOwnershipScope()` ganhou a opção `technicianRelationField` para filtrar via Prisma `{ some: { technicianId } }` (em vez de igualdade direta), e `assertOwnership()` passou a receber `technicianIds: string[]` — usado no RBAC de técnico em `GET /schedules`, `GET /schedules/:id` e `PATCH /schedules/:id/status`.
- **`Schedule.orderNumber` sequencial**: coluna `Int @unique @default(autoincrement())`, usada só para exibir um número de referência legível no PDF de Ordem de Serviço (não é chave nem usado em lógica de negócio). A sequência do Postgres foi ajustada via `setval` na própria migration para que o primeiro agendamento criado depois dela recebesse `160` — continuando a numeração que a Alvim já usava no sistema anterior; agendamentos existentes ficaram com números baixos (1..N), irrelevante por serem dados de teste.
- **PDF de "Ordem de Serviço" gerado no cliente**: botão "Gerar PDF" na tela de edição do agendamento (`/agendamentos/:id`) monta o PDF inteiramente no browser (`apps/web/lib/pdf/service-order.ts`, via `jspdf` + `jspdf-autotable`), sem endpoint de backend — todos os dados (cliente, técnicos, pontos, compostos) já vêm no `ScheduleDto`. O logo (`apps/web/public/logo.jpg`) é carregado como `data:` URL via `<canvas>` antes de `doc.addImage()`. Uma tabela por ponto de amostragem lista os compostos e a quantidade de amostras esperada.
- **PDF de "Ordem de Serviço" gerado no servidor (para e-mail)**: `apps/backend/src/modules/schedules/application/schedule-pdf.util.ts` reimplementa o mesmo layout do PDF acima, mas em Node (sem DOM/canvas) — o logo é lido direto do disco (`apps/backend/assets/logo.jpg`) e convertido para base64 via `fs.readFileSync`. Existe como arquivo separado (não compartilhado com o cliente) porque `packages/shared` é só tipos/enums (ver decisão em "Estrutura do Monorepo"), então uma lib com dependência de runtime (`jspdf`) não cabe lá; a duplicação de ~100 linhas de layout foi aceita em troca de manter essa fronteira.
- **Botão "Enviar agendamento para cliente" (`POST /schedules/:id/send-to-client`)**: gera o PDF acima no servidor e envia por e-mail (via Resend, `MailModule`) para dois grupos combinados (deduplicados por e-mail): usuários papel CLIENT ativos vinculados àquela empresa (`ClientUser`) e a equipe interna da Alvim (`UserRepository.findEmailRecipientsForInternalStaff()` — papéis ADMIN e MANAGER/"Gestor"), ambos com `User.emailNotifications = true`. Assunto fixo: `Agendamento {empresa} {dd/mm/aaaa} - Alvim Análises`. O e-mail inclui o PDF em anexo e um link para `WEB_APP_URL/agendamentos/:id`. Sem nenhum destinatário elegível (nem cliente, nem interno), retorna erro; sem `RESEND_API_KEY` configurada, `MailService` falha com uma mensagem clara em vez de silenciosamente não enviar.
- **`User.emailNotifications`**: preferência booleana (default `true`) de receber e-mails automáticos — hoje só consultada pelo fluxo acima, editável no `UserForm` quando o papel é Cliente.
- **Domínio verificado no Resend + remetente por fluxo**: `alvimanalises.com.br` foi verificado no Resend (DKIM/SPF/MX sob o subdomínio técnico `send.alvimanalises.com.br` — não é uma caixa de e-mail real, só existe para autenticação; DMARC opcional também configurado). `MailService.send()` aceita um `from` opcional por chamada (cai para `mail.fromEmail` da config quando omitido), permitindo que cada fluxo automático use seu próprio remetente — hoje `agendamentos@alvimanalises.com.br` para Ordem de Serviço (constante `SCHEDULE_EMAIL_FROM` em `send-schedule-to-client.use-case.ts`); um futuro envio de certificado usaria algo como `resultados@alvimanalises.com.br` do mesmo jeito, sem precisar verificar nada de novo no Resend (a verificação é por domínio, não por endereço).
- **"Agendamento" vs. "Realizados" é só um filtro de data, não um campo/status novo**: no menu, "Serviços" agrupa dois itens (`NavItem.children` em `role-permissions.ts`) — Agendamento (`/agendamentos`) e Realizados (`/agendamentos/realizados`) — que renderizam a mesma entidade `Schedule` através do mesmo componente `ScheduleListView.tsx`, cada um passando um `filter` diferente. `isScheduleRealized()` (`apps/web/lib/schedule-date.ts`) compara `scheduledDate` contra a meia-noite UTC equivalente ao dia de calendário local atual: hoje ou antes → Realizados, só data estritamente futura → Agendamento (o dia do serviço já conta como realizado, não precisa esperar o dia seguinte). Como é derivado (não persistido), reagendar um serviço passado para uma data futura na tela de edição já o move de volta pra Agendamento automaticamente — não existe transição de estado para implementar, só a mesma lista filtrada de outro jeito. `Sidebar.tsx` ganhou suporte a grupos expansíveis (`NavItem.children`), que abrem sozinhos quando uma rota filha está ativa.
- **Ações movidas para a tela de edição**: a listagem de `/agendamentos` e `/agendamentos/realizados` ficou só com "Editar" (mais "Resultados" em Realizados, ver abaixo); "Gerar PDF", "Enviar agendamento para cliente" e "Excluir"/"Reativar" ficam todos juntos no cabeçalho de `/agendamentos/:id`, para não poluir a tabela com muitos botões por linha.
- **Módulo de Resultados Analíticos**: `Sample` já era "uma análise coletada numa visita" (composto + ponto + data), então virou o dono natural de dois conceitos novos em vez de criar uma entidade paralela:
  - `Sample.sampleCode` (código do laboratório, opcional) e `Sample.analysisStatus` (`AnalysisStatus`: PENDING/IN_ANALYSIS/COMPLETED — "Pendente"/"Em análise"/"Concluída") — o andamento da análise em si, independente de já ter certificado anexado.
  - `SampleResultRow` (nova tabela, 1:N com `Sample`, `onDelete: Cascade`): uma linha por composto específico medido dentro da análise (ex.: "D4"/"Benzeno"), com `result` como **texto livre** (nunca número — preserva notação de laudo tipo `"< 0,01"`), `unit`, `specLimit` opcional, `compliance` (`ComplianceStatus`: CONFORME/NAO_CONFORME) opcional. Nome escolhido para não colidir com o model `Compound` (que é o "tipo de análise", ex. Siloxanos — um bucket diferente do composto individual medido). Substituído inteiro numa transação via `PUT /samples/:id/results` (mesmo padrão "apaga e recria" já usado em pontos de amostragem/técnicos/empresas de usuário) — não há diff linha a linha.
  - `Certificate` (já existia como stub) ganhou `analysisDate` (quando o laboratório analisou) **distinto** de `issueDate` (quando o documento foi emitido — datas diferentes por pedido explícito do usuário), `fileId` virou obrigatório (a linha só existe pra representar um arquivo enviado — seguro reforçar porque a tabela nunca teve linha em produção), e `responsibleUserId` ganhou relação de verdade com `User` (era uma string solta sem FK no stub original). Continua sem `@unique` em `sampleId`: uma amostra pode ter vários certificados (histórico de versões/substituições), cada `PATCH /certificates/:id/file` cria um novo `Attachment`, aponta o certificado pra ele e só apaga o arquivo físico antigo depois que o banco confirma a troca.
  - Índices adicionados em `Sample` (`compoundId`, `samplingPointId`, `collectionDate`) e `Certificate` (`sampleId`) — Postgres não indexa FK automaticamente, e essas colunas são exatamente os filtros que um dashboard histórico (fase futura, não construída agora) vai precisar; cliente/serviço/ponto/tipo de análise já são alcançáveis via `Sample` sem coluna nova.
  - **"Copiar estrutura do serviço anterior"** (`POST /samples/copy-previous-structure`): acha o schedule mais recente do mesmo cliente (excluindo o alvo) com pelo menos uma amostra ativa, e recria a mesma estrutura (`samplingPointId`/`compoundId` de cada `Sample`, `parameterName`/`unit`/`specLimit` de cada `SampleResultRow`) no schedule novo — sem copiar resultado, certificado, observação ou data (fica com a data do schedule alvo, status volta a PENDING). Sem histórico anterior, retorna `{ copied: false }` — não é erro, é o estado esperado quando o botão aparece (só aparece se o schedule alvo ainda não tem amostras).
  - **Upload de arquivo é o primeiro endpoint multipart do backend**: `certificates.controller.ts` usa `FileInterceptor('file')` (`@nestjs/platform-express`, já instalado; `@types/multer` adicionado como nova devDependency). `FileStorageService` ganhou `getStream()` (só tinha `upload`/`getUrl`/`delete`) pra servir o download via `stream.pipe(res)`.
  - **O proxy BFF genérico precisou de conserto pra suportar isso** (`apps/web/app/api/backend/[...path]/route.ts`): antes, forçava `Content-Type: application/json` em toda requisição e sempre fazia `JSON.parse()` na resposta — quebrava upload multipart (perdia o boundary) e download binário (tentava fazer JSON.parse de um PDF). Agora repassa o `Content-Type` original da requisição e só faz `JSON.parse` na resposta quando o `Content-Type` do backend for `application/json`, devolvendo bytes crus (com `Content-Disposition` preservado) caso contrário. Also faltava o handler `PUT` nesse arquivo (só tinha GET/POST/PATCH/DELETE) — sem ele, `PUT /samples/:id/results` retornava 405 pelo proxy mesmo com a rota existindo no backend.
  - Web: nova tela `/agendamentos/:id/resultados` (link "Resultados" só em `/agendamentos/realizados` — via `showResultsLink` em `ScheduleListView.tsx` — já que só faz sentido lançar resultado de um serviço já realizado; não aparece na listagem de Agendamento). Estrutura em acordeão, agrupada por ponto de amostragem: para cada `ScheduleSamplingPointCompound`, a tela renderiza `Math.max(compound.quantity, amostrasJáCriadas)` "slots" (`AnalysisSlot.tsx`) — um por instância de amostra esperada (ex.: Siloxanos com `quantity: 2` vira dois slots, "Amostra 1 de 2"/"Amostra 2 de 2"). As amostras já existentes daquele ponto+composto são ordenadas por `createdAt` e casadas 1:1 com os slots pela posição (a i-ésima amostra criada ocupa o slot i) — é um pareamento por ordem de criação, não uma FK "slot index" nova no banco. Cada slot vem fechado por padrão (`isOpen` local); abrir revela um mini-formulário de criar amostra (se o slot ainda não tem uma) ou o card completo (`SampleResultCard.tsx`: metadados editáveis inline, `CertificateList.tsx`/`CertificateUploader.tsx`, `ResultsTable.tsx`) se já tem. Amostras que não correspondem a nenhum ponto/composto configurado no agendamento (cadastradas fora do fluxo de slots, ex. via `/amostras/novo`) aparecem à parte, numa seção "Outras análises", pra não sumirem da tela. Download é um link `<a href>` direto pro proxy (sem JS extra) — o `Content-Disposition: attachment` do backend já força o download e os cookies httpOnly viajam sozinhos numa navegação same-origin.
- **"Amostras" virou "Cadeia de Custódia"**: a tela `/amostras` deixou de listar `Sample` por composto e passou a ser um repositório de PDFs organizado por composto → ano (`CustodyDocument`, novo model — espelha a estrutura de pastas que a Alvim já usa no OneDrive: `Amostragem de Campo > {composto} > {ano}`). Sem vínculo de empresa/cliente (os arquivos de origem já misturam clientes na mesma pasta de ano), por isso a rota saiu do RBAC do papel `CLIENT` em `role-permissions.ts` (ficou só ADMIN/MANAGER) — diferente de `Certificate`, aqui não há `assertOwnership` porque não há dono. Estrutura do módulo (`modules/custody-documents/**`) é uma réplica direta de `modules/certificates` (mesmo padrão Attachment-obrigatório, delete real sem soft-delete), só mais simples por não ter ownership/versão/data dupla. Importação inicial dos PDFs reais (474 arquivos de Siloxanos 2024-2026) feita via `apps/backend/scripts/import-custody-documents.ts` (roda com `ts-node`, só lê os arquivos de origem, nunca move/apaga do OneDrive) — reaproveitável pros outros 13 compostos passando outro `compoundCode`/pasta.
- **Bug de encoding em nome de arquivo multipart (descoberto durante a importação em massa)**: `busboy` (usado por `multer`/`@nestjs/platform-express`) decodifica os bytes do cabeçalho multipart como Latin-1 e nunca reconverte o parâmetro `filename` pra UTF-8 — diferente dos valores de campo de texto, que passam por essa conversão. Navegadores reais e o `FormData` nativo do Node mandam o filename em UTF-8 puro (sem RFC 5987 `filename*=`), então nomes com acento chegavam corrompidos (ex.: "Custódia" virava "CustÃ³dia") tanto em `certificates` quanto em `custody-documents` — bug pré-existente na feature de Certificados desta mesma sessão, só descoberto agora porque a importação em massa expôs muitos nomes acentuados de uma vez. Corrigido com `common/utils/multipart-filename.util.ts` (`fixMultipartFilename`, reverte o round-trip Latin-1→UTF-8) aplicado logo no início de todo use-case que recebe `Express.Multer.File` (`upload-certificate`, `replace-certificate-file`, `upload-custody-document`) — idempotente pra nomes puramente ASCII.
- **`GET /custody-documents/:id/view`**: mesmo arquivo do download, só que com `Content-Disposition: inline` em vez de `attachment` — abre o PDF direto na aba (link "Visualizar" e o próprio nome do arquivo, ambos com `target="_blank"`) em vez de forçar um download toda vez que alguém só quer conferir o conteúdo.
- **Pasta de composto virou pastas de ano** (`/amostras/composto/[compoundId]`): com centenas de PDFs por composto (ex. 552 em VOCs), listar tudo numa página só não escala — a tela agora lista os anos como subpastas (contagem por ano), e uma nova rota `/amostras/composto/[compoundId]/ano/[year]` mostra só os documentos daquele ano. O filtro por ano é client-side (`documents.filter(doc => doc.year === year)` sobre a mesma lista já buscada por composto) — não virou um novo parâmetro de query no backend, o volume por composto não justifica isso ainda.
- **Importação em massa dos 14 compostos** (11000 a 26000): rodado `import-custody-documents.ts` composto a composto — 1954 documentos no total. Um lote (VOCs) teve 20 falhas transitórias (`fetch failed`) por rodar 3 importações em paralelo ao mesmo tempo contra o backend local; isso motivou tornar o script idempotente (`findExistingKeys()` — compara `ano|filename` contra os documentos já cadastrados daquele composto antes de subir cada arquivo) pra poder simplesmente rodar de novo sem duplicar nada.
- **Botão "Atualizar pastas" (`POST /custody-documents/sync`)**: solução de transição enquanto a Alvim ainda mantém as cadeias de custódia no OneDrive no dia a dia, além de anexar direto na plataforma. Reaproveita a mesma lógica de dedup do script de importação, mas roda dentro do próprio backend (sem HTTP client interno, sem login) — varre `CUSTODY_DOCUMENTS_SYNC_ROOT` (env var, só faz sentido numa máquina que tem esse OneDrive montado localmente; sem ela configurada, o endpoint retorna 400 em vez de tentar ler um caminho inexistente), casa cada subpasta de primeiro nível com um `Compound` pelo código numérico no início do nome (`^(\d+)\s*-\s*.+$`), e sobe só os PDFs que ainda não existem (mesma chave `compoundId+ano+filename`). Tem uma trava simples (`running` em memória) pra não deixar duas sincronizações rodarem ao mesmo tempo. Não é sincronização de verdade (não detecta arquivo removido do OneDrive nem atualiza o que já existe) — só soma o que é novo, é clique manual (sem cron), e o objetivo é sumir quando o cadastro direto pela plataforma virar o único fluxo.
- **Digitalização inteligente de cadeia de custódia (MVP — só Siloxanos)**: automatiza o fluxo hoje manual (técnico preenche a cadeia de custódia à mão em campo → alguém redigita numa planilha → planilha gera o PDF final). Botão "Gerar Cadeia de Custódia" dentro de cada amostra em `/agendamentos/:id/resultados` (`SampleResultCard.tsx` → `CustodyExtractionSection.tsx`) deixa fotografar/escanear o formulário manuscrito; a plataforma lê os campos via IA, mostra numa tela de conferência (`/cadeia-custodia/:extractionId`) pra correção humana, e só gera o PDF oficial depois de aprovado.
  - **`CustodyFieldTemplate`** (novo model, 1:1 com `Compound`): define os campos esperados de um composto como JSON (`CustodyTemplateSchema` — lista de campos simples + uma tabela de colunas×linhas, ex. Siloxanos tem 4 colunas A/B/C/Branco × 4 linhas de impingers). Guardado como JSON (não colunas fixas) justamente pra caber layouts bem diferentes dos outros 13 compostos sem precisar de migration nova a cada um — só falta cadastrar o template deles (hoje via seed, `prisma/seed.ts`; um cadastro por UI fica pra depois). "Metodologia"/"Procedimento Interno" do formulário original ficaram de fora do template — são fixos do laboratório, não variam por coleta.
  - **`CustodyExtraction`** (novo model, N:1 com `Sample` e com `CustodyFieldTemplate`): uma linha por upload de scan. Guarda o arquivo original (`Attachment`, sempre — nunca só o PDF final, pra rastreabilidade/auditoria), o JSON bruto que a IA leu (`extractedData`, com `{value, confidence}` por campo) e, se o técnico corrigiu algo, `correctedData` (mesma forma; `null` até a primeira edição). Estados: `PROCESSING` → `NEEDS_REVIEW` (ou `FAILED`, com `errorMessage` claro) → `APPROVED`. Na aprovação usa `correctedData ?? extractedData` — o técnico pode aprovar sem editar nada se a leitura já veio certa.
  - **Leitura via Claude Vision** (`modules/custody-extractions/infrastructure/claude-ocr.service.ts`, `@anthropic-ai/sdk`): manda a imagem/PDF escaneado (aceita os dois nativamente como content block, sem rasterizar PDF em imagem) + um prompt com a lista de campos do template, pedindo JSON estrito `{fields, table}` com `value`/`confidence` por campo — instruído a nunca inventar valor (string vazia + confidence 0 quando ilegível). Chamada **síncrona dentro do mesmo request** (sem fila de job — a app não tem infra de background job ainda, e a leitura leva poucos segundos); erro de rede ou JSON mal formado vira `FAILED` em vez de 500. Sem `ANTHROPIC_API_KEY` configurada, falha com mensagem clara (mesmo padrão do `MailService`/`RESEND_API_KEY`) — testado e confirmado: com uma chave de outro provedor (Gemini) colada por engano, a IA simplesmente não seria chamada com o SDK certo, por isso a troca de provedor exigiria reescrever `ClaudeOcrService` inteiro, não só trocar a env var.
  - **Verificado com os PDFs reais de referência** (a cadeia de custódia manuscrita de Siloxanos e sua versão final "FT-14"): a IA leu corretamente empresa, endereço, amostrador, datas, horários, e as 4 colunas da tabela de impingers — inclusive lendo "Alvim 006" da letra manuscrita (não "Alvim 007", que é o que está na versão final digitada — a leitura reflete o papel real, não a transcrição "oficial"), e marcando com confiança baixa exatamente os campos que estavam ilegíveis/em branco no original (ex. "XXXX" no número de relatório, que é um placeholder no formulário).
  - **`CustodyDocument` ganhou `sampleId` opcional**: o PDF gerado por este fluxo fica vinculado à amostra de origem e continua caindo na mesma pasta composto/ano já existente (`ApproveCustodyExtractionUseCase` reaproveita `CUSTODY_DOCUMENT_REPOSITORY.create()` do módulo `custody-documents`) — os ~1954 documentos importados do OneDrive continuam com `sampleId: null`, sem quebrar nada.
  - **PDF final replica o modelo em branco oficial da Alvim** (`custody-extraction-pdf.util.ts`, jsPDF + `jspdf-autotable`): decisão revista depois que o usuário mandou o modelo em branco real, primeiro em PDF ("11000 - Cadeia de custódia Silox (MODELO DE CAMPO).pdf") e depois o `.xlsx` original — logo + título, tabela de controle de documento (Responsável/Emissão/Revisão, `CustodyTemplateSchema.documentMeta`), linha "relatorio de campo n° / composto / DATA" (`topRowFieldKeys`). Título com auto-encolhimento de fonte (`doc.getTextWidth` em loop) pra nunca sobrepor a tabela de controle de documento — bug real visto no primeiro PDF gerado, corrigido antes de virar padrão. `getLogoBase64()` extraído pra `common/utils/pdf-logo.util.ts`, compartilhado com `schedule-pdf.util.ts` (Ordem de Serviço).
  - **Estrutura da tabela corrigida a partir do `.xlsx` original** (sem ferramenta de Python funcional no ambiente pra usar `openpyxl` — o `.xlsx` foi inspecionado direto como zip/XML, `unzip` + leitura de `sheet1.xml`/`styles.xml`/`sharedStrings.xml`): o primeiro PDF gerado (baseado só numa captura de tela do modelo) tinha dois erros estruturais reais que o usuário notou comparando com o modelo — um cabeçalho "A/B/C/Branco" com fundo cinza na tabela de amostragem que não existe no original, e essa tabela separada da tabela de campos. O Excel mostra que é **uma única tabela contínua**: coluna A é o rótulo (58.66 de 126.3 de largura total ≈ 46,4%), colunas B–E são a área de valor, mescladas numa célula só (`colSpan: 4` no jspdf-autotable) pra quase todo campo, mas viram 4 células de verdade só nas 4 linhas da tabela de amostragem (`schema.tableInsertAfterKey` marca onde essas linhas entram no meio da lista de campos) — sem cabeçalho novo ali, só as mesmas bordas finas pretas do resto da tabela. Sem nenhuma cor de preenchimento no modelo inteiro (só o texto "RECUPERADO" em vermelho, não replicado ainda).
  - **Campos fixos e campo gerado pelo sistema** (`CustodyTemplateField.fixedValue`/`.systemGenerated`): o modelo em branco já vem com "Responsável pela Amostragem/empresa/fone", "Metodologia" e "Procedimento Interno" pré-impressos — não variam por coleta, então saíram da lista perguntada à IA (`ClaudeOcrService` filtra `fixedValue !== undefined` antes de montar o prompt) e da tela de conferência (aparecem como texto fixo, não input). "Relatório de Campo nº" é parecido mas dinâmico: no papel é só um placeholder "XXXX" — o valor de verdade é atribuído pelo backend na aprovação (`computeNextReportNumber()` em `approve-custody-extraction.use-case.ts`), continuando a sequência já usada pelo composto+ano. Como os ~1954 documentos importados do OneDrive seguem o padrão de nome `{número}_{aa} - ...`, a próxima sequência é achada só olhando o maior prefixo numérico entre os nomes de arquivo já cadastrados naquele composto+ano (sem coluna dedicada pro número) — os documentos gerados por este fluxo usam o mesmo padrão de nome, então a numeração continua consistente entre os dois fluxos.
  - **`CustodyDocument.sampleId` de fato preenchido na aprovação** (`custodyDocumentRepository.create({..., sampleId: sample.id})`) — um descuido da primeira versão (o campo existia no schema mas não era passado) só notado ao revisar o use-case pra essa mudança.
  - **RBAC inclui `TECHNICIAN`** (diferente de `custody-documents`, que é só ADMIN/MANAGER): aqui a extração tem dono via `Sample.clientId` (`assertOwnership`), e é o técnico de campo quem de fato fotografa e sobe a cadeia de custódia.
- **"Fotos do Serviço" completa o módulo `service-executions`, que era só stub** (schema/repositório mínimo desde a fase 1, sem controller/rota — ver `ARCHITECTURE.md` histórico). Botão em `/agendamentos/:id/resultados` abre uma galeria (`ServicePhotosSection.tsx`) de fotos gerais da visita (inclusive de amostras), com dono via `Schedule.clientId`. `ServiceExecution` (1:1 com `Schedule`, `technicianId`/`executionDate` obrigatórios no schema) é criado sob demanda no primeiro upload (`UploadServicePhotoUseCase` — `findByScheduleId` ?? `create({technicianId: user.id, executionDate: schedule.scheduledDate})`) em vez de exigir um fluxo de checklist prévio que não foi pedido nesta etapa. Fotos são `Attachment` comuns (`kind: PHOTO`) ligadas por `serviceExecutionId`.
- **Foto opcional na cadeia de custódia, abaixo de "Observações"**: `CustodyExtraction.selectedPhotoId` (novo campo, FK opcional pra `Attachment`) guarda qual foto do serviço foi escolhida na tela de conferência (`PATCH /custody-extractions/:id/photo`, `SelectCustodyExtractionPhotoUseCase`) — a lista de fotos candidatas vem do mesmo `Schedule` da amostra, por isso `CustodyExtractionDto` ganhou `scheduleId` (via `sample.scheduleId`, incluído no `INCLUDE_RELATIONS` do repositório). Na aprovação, `ApproveCustodyExtractionUseCase` lê os bytes da foto (`FileStorageService.getStream()` + `streamToBuffer()`) e passa pro gerador de PDF; `custody-extraction-pdf.util.ts` usa `doc.getImageProperties()` do próprio jsPDF (aceita `Buffer` diretamente, sem lib extra de imagem) pra escalar preservando proporção — largura fixa = largura do conteúdo, altura máxima 260pt ("de forma homogênea", mesmo padrão de posição/tamanho toda vez, independente da imagem) — e pula pra nova página se não couber no espaço restante.

## 5. Autenticação e autorização

- **JWT de acesso** (15 min) + **refresh token** (7 dias) com **rotação**: a cada `/auth/refresh`, o token anterior é revogado e um novo par é emitido. Apenas o hash (SHA-256) do refresh token fica no banco — nunca o token em texto puro.
- **Senhas**: bcrypt (custo 10).
- **Guards globais**: `JwtAccessGuard` (via `APP_GUARD`) exige token válido em toda rota, exceto as marcadas com `@Public()` (login, refresh). `RolesGuard` + `@Roles(...)` controlam por papel em cada rota.
- **Escopo por Cliente/Técnico — decisão deliberada**: aplicado explicitamente na camada de aplicação (`common/utils/scope.util.ts` — `applyOwnershipScope()` para listagens, `assertOwnership()` para recurso único), e **não** via middleware global do Prisma. Um middleware global reescrevendo queries silenciosamente é implícito, difícil de testar isoladamente, e exigiria plumbing de `AsyncLocalStorage` para saber "quem é o usuário atual" dentro do Prisma. Manter o ponto de escopo visível em cada use-case é mais simples de auditar e testar.

### Usuário-cliente com acesso a múltiplas empresas (N:N)

Um usuário (pessoa, papel CLIENT) pode ter acesso a mais de uma empresa (`Client`) — ex.: um contador ou responsável que atende várias empresas-cliente. Modelado como tabela de junção explícita `ClientUser` (`userId`, `clientId`, `@@unique`), não uma relação implícita do Prisma, para poder anexar metadados no futuro (papel dentro da empresa, data de concessão de acesso etc.) sem migration extra.

- **JWT carrega `clientIds: string[]`** (todas as empresas do usuário), não um `clientId` fixo. Qual empresa está "ativa" é decidido **por requisição**, via query param `?clientId=`, e não fica embutido no token — assim trocar de empresa no seletor do portal não exige novo login nem refresh.
- **`resolveActiveClientId(user, requestedClientId)`** (`common/utils/scope.util.ts`) valida que o `clientId` pedido está em `user.clientIds` (senão `403`); se nenhum for informado, usa o primeiro da lista como padrão — mantém endpoints funcionando mesmo sem o seletor (ex.: chamadas do mobile, que ainda não tem seletor de empresa).
- **Endpoints afetados**: `GET /contracts` e `GET /schedules` aceitam `?clientId=`; endpoints de recurso único (`GET /contracts/:id` etc.) usam `assertOwnership()`, que permite acesso se o recurso pertencer a **qualquer uma** das empresas do usuário (não só a "ativa").
- **`GET /clients/me`** retorna a **lista** de empresas do usuário logado (não mais um objeto único) — usada para popular o seletor.
- **Web**: `lib/auth/ActiveClientContext.tsx` busca as empresas do usuário e guarda a selecionada em `localStorage` (sem round-trip ao servidor); `components/layout/EmpresaSwitcher.tsx` é o `<select>` no cabeçalho do portal, visível só para CLIENT. Páginas de Contratos/Agendamentos incluem a empresa ativa na `queryKey` do TanStack Query, então trocar no seletor já refaz a busca.
- **Gestão pelo Admin**: `UserForm` mostra uma lista de checkboxes de empresas (só as `ACTIVE`) quando o papel selecionado é Cliente; `PrismaUserRepository.update()` substitui o conjunto inteiro de vínculos dentro de uma transação (`deleteMany` + `create`) quando `clientIds` é enviado — não é um "adicionar".
- **Mobile**: ainda não tem seletor de empresa — usa o comportamento padrão (primeira empresa do usuário). Fica como próximo passo caso o app do técnico/cliente precise da mesma troca que o web tem.

### Fronteira Gestor × Administrador

- **Administrador**: acesso total, incluindo criar/editar/desativar usuários e atribuir papéis.
- **Gestor**: CRUD completo em Clientes, Contratos e Agendamentos; **somente leitura** em Usuários (precisa listar para atribuir técnico a um agendamento), mas não pode criar/editar usuários nem alterar papéis. Gestão de usuários/papéis é um vetor de escalação de privilégio — fica reservada ao Administrador por design.

### Armadilhas conhecidas (encontradas na verificação end-to-end)

- **Campos opcionais vazios do formulário**: `@IsOptional()` do class-validator só trata `null`/`undefined` como "ausente" — um `<input>` HTML vazio envia `""`. `common/pipes/empty-string-to-undefined.pipe.ts` (registrado globalmente antes do `ValidationPipe` em `main.ts`) converte `""` → `undefined` em todo body de requisição, para não quebrar validadores como `@IsEmail()` opcional.
- **CORS multi-origem**: `CORS_ORIGIN` no `.env` aceita uma lista separada por vírgula (`configuration.ts` faz o split). Necessário porque o mobile em modo web (`expo start --web`, porta 8081) é uma origem de browser diferente do painel Next.js (porta 3000) — ambas precisam estar liberadas em dev.
- **Redirect pós-login/guard nunca deve ser fixo em `/dashboard`**: Técnico e Cliente não têm acesso a `/dashboard` (ver `NAV_ITEMS`). Use sempre `getDefaultRouteForRole(role)` (`packages/shared/src/constants/role-permissions.ts`) — tanto no middleware do web quanto na página de login — para não criar um loop de redirecionamento.
- **Guard de "só na primeira renderização" com `useRef(true)` não sobrevive ao StrictMode**: `next.config.js` tem `reactStrictMode: true`, que duplica a invocação de efeitos no mount em dev (mount → cleanup → mount de novo) para expor efeitos não-idempotentes. Um padrão como `const isFirstRender = useRef(true); useEffect(() => { if (isFirstRender.current) { isFirstRender.current = false; return; } ... })` quebra nesse cenário: a segunda invocação simulada já vê o ref como `false` e executa a lógica "de verdade" mesmo sendo ainda o mount inicial — foi o que zerava a seleção de pontos de amostragem já salva ao abrir `/agendamentos/:id` para editar. Corrigido em `ScheduleForm.tsx` guardando o **último valor conhecido** da dependência (`lastClientIdRef`) em vez de um booleano "já rodou uma vez": só dispara a limpeza quando o valor de fato mudou, o que é idempotente a qualquer número de invocações do efeito.
- **react-hook-form vaza campos não registrados**: passar o DTO inteiro como `defaultValues` de um formulário de edição (`useForm({ defaultValues: dto })`) faz campos como `id`/`createdAt`/`updatedAt` sobreviverem até o `onSubmit`, e o backend rejeita (`forbidNonWhitelisted`). Os formulários em `apps/web/components/forms/` sempre constroem `defaultValues` explicitamente, campo a campo — siga o mesmo padrão em formulários novos.
- **`expo-secure-store` não funciona no target web** (só iOS/Android nativos). `apps/mobile/lib/auth/storage.ts` verifica `Platform.OS === 'web'` e usa `localStorage` nesse caso.

## 6. Abstração de armazenamento de arquivos

`modules/attachments/domain/file-storage.interface.ts` define a porta `FileStorageService` (`upload`, `getUrl`, `delete`). O adapter atual (`LocalFileStorageService`) grava em `apps/backend/storage/`. Para trocar por S3/Supabase Storage no futuro, basta implementar a interface num novo adapter e mudar o binding em `attachments.module.ts` — nenhum outro módulo precisa mudar.

## 7. Frontend web

- **Um único Next.js app**, não um app por papel: todos os papéis compartilham autenticação, design e a maior parte das telas de CRUD (o que muda é o menu/colunas visíveis, não a stack). Route groups `(auth)` e `(portal)` separam a tela de login do restante.
- **Padrão BFF**: `app/api/auth/login` e `app/api/auth/logout` fazem proxy para o backend e setam os tokens como cookies **httpOnly** — inacessíveis a JS no browser (mitigação XSS). `app/api/backend/[...path]/route.ts` é um proxy genérico usado por todas as chamadas de API feitas por Client Components: anexa o `Authorization: Bearer`, e se receber 401, tenta renovar via refresh token automaticamente antes de repassar a resposta.
- **TanStack Query** para data-fetching/cache/mutations nas telas de CRUD.
- **`middleware.ts`** (raiz do app, não dentro de `app/`) protege rotas: sem sessão válida redireciona para `/login`; com sessão mas sem permissão de papel para a rota, redireciona para `/dashboard`. Usa `canAccessRoute()` de `packages/shared`.

## 8. Mobile

- Mesma convenção de pastas do app de RH já existente da empresa (`(auth)` e `(app)`), mas é um projeto Expo novo, sem código reaproveitado.
- Tokens em `expo-secure-store`; `lib/api/client.ts` usa um interceptor Axios que renova o access token automaticamente em respostas 401.
- Nesta fase, as telas de Técnico (`meus-agendamentos`) e Cliente (`meus-servicos`) são **somente leitura** — o backend já devolve os dados escopados por RBAC, a tela só renderiza.

## 9. Como estender — adicionando um novo módulo completo

1. Criar `modules/<nome>/domain/<nome>.repository.ts` com a interface do repositório e o símbolo de DI.
2. Criar `modules/<nome>/infrastructure/prisma-<nome>.repository.ts` implementando a interface.
3. Criar DTOs em `application/dto/` com `class-validator`.
4. Criar um use-case por operação em `application/use-cases/` (create, list, get, update, delete) — cada um recebe a interface do repositório via `@Inject(TOKEN)`.
5. Criar `infrastructure/<nome>.controller.ts` com `@Roles(...)` em cada rota, chamando os use-cases.
6. Registrar tudo em `<nome>.module.ts` e importar no `AppModule`.
7. Se o módulo tiver tipos/DTOs usados pelo frontend, adicioná-los em `packages/shared/src/types/`.
8. No web, criar `lib/api/<nome>.api.ts` (usa o proxy `/api/backend/...`) e as telas em `app/(portal)/<nome>/`.

Se o módulo já existe como **stub** (ex.: `samples`, `certificates`), os passos 1–2 já estão prontos — comece do passo 3.
